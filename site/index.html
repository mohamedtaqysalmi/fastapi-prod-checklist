A FastAPI template where every production requirement has a test.

Most "production-ready" templates are a README and a promise. Here each requirement, such as a health endpoint, request IDs, safe CORS or a non-root container, has a test that fails if someone removes it. I built it as a starting point I can trust and a checklist I can point to.

    What works

    This is what v0.1.0 does today, including the parts that are only half checked.

    • works App factory with settings validated at startup, /healthz and /readyz, request IDs, JSON logs, one error body, CORS and security headers
    • works Rate limiting, opt-in Sentry, graceful shutdown and Alembic migrations
    • partial The Dockerfile is multi-stage and runs as UID 10001, but CI only parses the file. It does not build the image.
    • partial Rate limiting counts requests inside one process. It does not work across several workers.
    • not done CORS headers on 500 responses, shared-store rate limiting, a Lighthouse score for this page

    Quickstart

    git clone https://github.com/mohamedtaqysalmi/fastapi-prod-checklist
cd fastapi-prod-checklist
cp .env.example .env
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
uvicorn app.main:create_app --factory --no-access-log

    APP_ENVIRONMENT is required and has no default. For Docker, run docker compose up --build.

    04

    How it works

    create_app() in src/app/main.py stacks the middleware in this order, outermost first. Request context and security headers sit outside the rate limiter so a 429 still gets a request ID and headers. 

    client
  │
  ▼
in-flight tracker      shutdown waits for open requests
  │
security headers       also on error responses
  │
request context        request ID, access log, 500 body
  │
rate limiter           429 in the shared error shape
  │
CORS                   only when origins are configured
  │
  ▼
routes                 /healthz  /readyz
    05

    How I built it

    Tests check behaviour, not names

    The readiness tests send HTTP requests and read settings. They do not import internal helpers, so renaming a function cannot hide a removed feature. I checked this by deleting features and watching the matching test fail.

    Unhandled errors are caught in my own middleware

    Starlette runs its catch-all handler outside the middleware stack, so a 500 built there would lose the request ID and security headers. Catching the error one layer in keeps them. The cost is that 500s miss CORS headers, which is listed below.

    Sentry is opt-in

    Nothing is sent unless APP_SENTRY_DSN is set, and it starts with send_default_pii off. A clone of the template should not report events by accident.

    Some requirements are files, so those tests read files

    The non-root user and the Alembic setup are checked by parsing the Dockerfile and running alembic upgrade head on a SQLite file. That is weaker than building the image, and I say so above.

    06

    Limits and roadmap

    • Unhandled 500 responses do not carry CORS headers.
    • Log redaction works by key name. A secret inside a free-text message is not caught.
    • The interactive API docs are off, because the strict CSP would block them.
    • The Docker healthcheck calls /healthz, so it does not prove readiness.

    Planned work is tracked in the v0.2.0 milestone. To contribute, start with CONTRIBUTING.md.
